# Refactoring mdship CLI and MCP Integration

Date: 2026-07-30

## Purpose

This document describes a focused refactoring of mdship so that the command-line
interface and MCP server are thin interfaces over the same application
implementation.

The refactoring does not add plugins or change placeholder syntax. Its purpose is
to remove duplicated file handling and command orchestration, eliminate behavioral
differences between CLI and MCP operations, and establish a stable starting point
for later development.

## Executive Summary

The low-level Markdown algorithms are already mostly shared. Both `mdship/cli.py`
and `mdship/mcp_server.py` call functions from `mdship/markdown.py`.

The duplication is one level above those algorithms:

- Reading and validating files
- Comparing original and generated content
- Creating backups
- Writing files
- Applying dry-run and tracking policies
- Running the complete `update` pipeline
- Interpreting errors
- Reporting changed artifacts and notices

The proposed structure is deliberately small:

```text
CLI ──┐
      ├──> operations.py ──> markdown.py
MCP ──┘
```

- `markdown.py` remains the content-processing implementation.
- A new `operations.py` module implements file-level mdship use cases.
- `cli.py` parses CLI input and renders human-readable output.
- `mcp_server.py` defines MCP tools and serializes operation results.

The CLI and MCP interfaces do not need to expose exactly the same commands. When
they expose the same operation, however, they must call the same implementation.

## Current Structure

### `mdship/markdown.py`

This module contains the core Markdown and placeholder-processing functions,
including:

- `fix_heading_levels`
- `shift_heading_levels`
- `add_content_checksum`
- `check_content_checksum`
- `reflow_paragraphs`
- `add_heading_numbers`
- `remove_heading_numbers`
- `collect_set_variables`
- `update_includes`
- `replace_variables_in_document`
- `process_template`
- `process_jinja2`
- `insert_table_of_contents`
- `update_mermaid`
- AI placeholder functions

Most of these functions operate on strings and already provide a shared domain
implementation for both interfaces.

### `mdship/cli.py`

The CLI currently owns both interface concerns and application behavior:

- Typer argument and option declarations
- Multiple-file processing
- `.mdship/.lastfiles` handling
- File existence checks
- Reading and writing files
- Backup creation
- Dry-run handling and diff output
- Front-matter tracking
- Calling Markdown functions
- Running the complete placeholder update sequence
- Deciding which exceptions to suppress
- Formatting success, warning, and error messages
- Exit status selection

### `mdship/mcp_server.py`

The MCP server separately implements:

- File existence checks
- Reading files
- Backup creation
- Writing files
- Calling Markdown functions
- Running another copy of the complete placeholder update sequence
- Interpreting operation results
- Formatting MCP return strings

This means that the adapters do not merely expose the same implementation. Each
adapter partially implements mdship itself.

## Duplicated Operations

The following user-facing operations have implementations in both adapters:

| CLI command | MCP tool | Core function or operation |
|---|---|---|
| `fix-headings` | `fix_headings` | `fix_heading_levels` |
| `shift-headings` | `shift_headings` | `shift_heading_levels` |
| `sum` | `add_checksum` | `add_content_checksum` |
| `verify` | `check_checksum` | `check_content_checksum` |
| `reflow` | `reflow` | `reflow_paragraphs` |
| `semantic-line-breaks` | `semantic_line_breaks` | `reflow_paragraphs` with width zero |
| `number` | `number` | `add_heading_numbers` |
| `unnumber` | `unnumber` | `remove_heading_numbers` |
| `update` | `update` | Complete placeholder pipeline |
| `ai-fix` | `ai_fix` | `ai_fix_placeholders` |
| `ai-check` | `ai_check` | `ai_check_placeholders` |

Some operations intentionally exist in only one interface:

- CLI-only operations include `validate` and `init`.
- MCP-only operations include standalone `toc`, `include`, `mermaid`,
  `ai_context`, and `ai_update`.

That difference is not itself a problem. The problem is duplicated application
behavior for operations exposed through both interfaces.

## Existing Behavioral Differences

The duplicated implementations have already diverged.

### File writing

The CLI:

- Compares generated content with the original content
- Does not write unchanged content
- Does not create a backup for unchanged content
- Supports dry-run
- Supports front-matter tracking
- Reports whether a file changed

The MCP server:

- Writes the file even if the content is unchanged
- Creates a backup whenever requested, even for unchanged content
- Does not support dry-run
- Does not support tracking
- Does not report whether content actually changed

### The `update` pipeline

Both adapters manually execute the same phases:

1. Collect variables
2. Update includes
3. Replace variable references
4. Process `TEMPLATE`
5. Process `JINJA2`
6. Insert or update the table of contents
7. Render Mermaid diagrams

Differences include:

- CLI propagates `force`; MCP does not expose or propagate it.
- CLI propagates dry-run to Mermaid rendering.
- CLI collects the paths of changed Mermaid artifacts.
- CLI suppresses only the expected missing-TOC condition.
- MCP suppresses every `ValueError` raised by TOC processing.
- CLI avoids unnecessary document writes and backups.
- Error messages and failure behavior differ.

Suppressing every TOC `ValueError` in MCP is particularly risky. It can hide an
integrity failure, malformed marker, invalid configuration, or another genuine
processing error.

### Errors and result reporting

The CLI generally catches exceptions, prints errors, accumulates failed files, and
returns a nonzero exit status.

The MCP implementation varies between:

- Returning `"Error: ..."` strings
- Returning `"ERROR: ..."` strings
- Returning other status strings
- Allowing exceptions to escape

Application code should express success and failure consistently. The interfaces
should decide how those results are represented to their callers.

### Interface-specific document inspection

The CLI contains behavior such as:

- Detecting a likely single h1 document title
- Warning that heading-number changes may leave a TOC stale
- Combining link and AI placeholder validation

Some of these are presentation-oriented notices, but the CLI currently inspects
document content to produce them. Shared operations should return structured
notices when both interfaces could benefit from the information.

## Responsibility Boundaries

### Domain layer: `markdown.py`

The domain layer should:

- Transform Markdown content
- Parse and validate placeholders
- Check managed-content integrity
- Generate replacement content
- Return content or domain data
- Raise domain-specific exceptions

It should not:

- Know about Typer, Rich, or FastMCP
- Print output
- Choose process exit codes
- Return protocol-specific `"OK"` or `"ERROR"` strings
- Implement backup policy

### Application layer: `operations.py`

The application layer should:

- Validate file paths
- Read source files
- Invoke domain functions
- Run multi-step workflows such as `update`
- Apply tracking policy
- Compare original and resulting content
- Apply backup, dry-run, and write policy
- Collect artifact changes and notices
- Return structured results

It should not:

- Print Rich output
- Raise Typer exits
- Depend on FastMCP
- Format MCP response strings

Application operations should act on one document at a time. CLI-specific
multiple-file iteration and `.lastfiles` behavior can remain in the CLI.

### CLI adapter: `cli.py`

The CLI should:

- Declare Typer commands and options
- Parse CLI-specific syntax such as `--lines 10:50`
- Resolve explicit files or `.mdship/.lastfiles`
- Iterate over multiple input files
- Convert CLI options into application options
- Render diffs, notices, success messages, and errors
- Select exit codes

It should not import content-processing functions directly from `markdown.py`.

### MCP adapter: `mcp_server.py`

The MCP adapter should:

- Declare MCP tools and their schemas
- Convert MCP parameters into application arguments
- Call application operations
- Serialize structured results
- Convert application errors into MCP tool failures or structured errors

It should not import content-processing functions directly from `markdown.py`.

## Proposed Application API

The following API is illustrative. Exact names may change during implementation,
but the responsibility boundary should remain.

### Write options

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class WriteOptions:
    backup: bool = True
    dry_run: bool = False
    track: bool = False
```

`force` is a placeholder-processing option rather than a universal write option.
It should therefore be an explicit argument to operations that support it.

### Operation result

```python
from dataclasses import dataclass
from pathlib import Path


@dataclass(frozen=True)
class OperationResult:
    path: Path
    changed: bool
    written: bool
    before: str
    after: str
    artifacts: tuple[Path, ...] = ()
    notices: tuple[str, ...] = ()
```

The result contains facts rather than formatted messages:

- `changed` means the generated document differs from the original.
- `written` means the new content was committed to disk.
- In dry-run mode, `changed` may be true while `written` is false.
- `before` and `after` allow the CLI to generate a diff.
- `artifacts` contains changed files such as rendered diagrams.
- `notices` contains non-fatal information that adapters may display.

If retaining both full content strings becomes undesirable, the result can later
store a prepared diff or an optional before/after pair. The initial design should
favor clarity.

### Read-only result

Read-only commands should not encode failure in strings:

```python
@dataclass(frozen=True)
class CheckResult:
    path: Path
    ok: bool
    issues: tuple[str, ...] = ()
    notices: tuple[str, ...] = ()
```

Examples include checksum verification, link validation, and AI placeholder
checking.

### Shared file-edit helper

The application module should contain one internal helper for simple modifying
operations:

```python
def _edit_file(
    path: Path,
    transform: Callable[[str], str],
    *,
    operation: str,
    options: WriteOptions,
) -> OperationResult:
    ...
```

The helper should:

1. Validate that the path exists and is a regular file.
2. Read the source content once.
3. Invoke the transformation.
4. Apply tracking when enabled.
5. Compare original and generated content.
6. Return without writing or backing up when unchanged.
7. Return a planned result without writing in dry-run mode.
8. Create a backup when requested.
9. Write the generated content.
10. Return an `OperationResult`.

Named application operations then become small wrappers:

```python
def fix_headings_file(
    path: Path,
    *,
    options: WriteOptions = WriteOptions(),
) -> OperationResult:
    return _edit_file(
        path,
        fix_heading_levels,
        operation="fix-headings: fixed heading hierarchy",
        options=options,
    )
```

Named wrappers are preferable to having the interfaces call `_edit_file`
directly. They create a stable use-case API and keep knowledge of domain function
selection and tracking descriptions out of both interfaces.

## Canonical Update Workflow

The update pipeline should be extracted in two layers.

### Content-level workflow

```python
@dataclass(frozen=True)
class DocumentUpdate:
    content: str
    artifacts: tuple[Path, ...] = ()


def update_document(
    content: str,
    path: Path,
    *,
    force: bool = False,
    dry_run: bool = False,
) -> DocumentUpdate:
    ...
```

This function should be the only place that defines the update phase order.

Its initial behavior should follow the more careful CLI implementation:

1. `collect_set_variables`
2. `update_includes`
3. `replace_variables_in_document`
4. `process_template`
5. `process_jinja2`
6. `insert_table_of_contents`
7. `update_mermaid`

It should:

- Pass `force` consistently to every supporting phase.
- Pass `dry_run` to Mermaid processing.
- Collect changed Mermaid artifact paths.
- Ignore only a typed missing-TOC condition.
- Propagate malformed placeholder, integrity, rendering, and validation errors.

### File-level workflow

```python
def update_file(
    path: Path,
    *,
    force: bool = False,
    options: WriteOptions = WriteOptions(),
) -> OperationResult:
    ...
```

This function should:

- Read the document once.
- Call `update_document`.
- Apply tracking.
- Compare and commit the document.
- Return document and artifact changes in one result.

## Domain Exceptions

Expected conditions must not be distinguished by parsing exception messages.

The CLI currently recognizes a missing TOC by checking whether a `ValueError`
message begins with a particular string. MCP suppresses every TOC `ValueError`.
Both should be replaced with typed domain errors.

An initially small exception hierarchy is sufficient:

```python
class MdshipError(Exception):
    """Base class for expected mdship operation failures."""


class FileOperationError(MdshipError):
    """A source or destination file could not be processed."""


class PlaceholderError(MdshipError):
    """A placeholder was malformed or could not be processed."""


class PlaceholderNotFound(PlaceholderError):
    """The requested optional placeholder is not present."""


class IntegrityError(PlaceholderError):
    """Managed content failed an integrity check."""
```

The update workflow may suppress `PlaceholderNotFound` for an optional TOC. It
must not suppress `IntegrityError` or a general `PlaceholderError`.

Exceptions should contain useful context such as the path, placeholder type, and
line number where available. They should not contain Rich markup or MCP response
formatting.

## Example Thin Interfaces

### CLI

Conceptually, the CLI update command should become:

```python
for file in _resolve_files(files):
    try:
        result = operations.update_file(
            file,
            force=force,
            options=WriteOptions(
                backup=not state.no_bak,
                dry_run=state.dry_run,
                track=state.track,
            ),
        )
        _render_result(result)
    except MdshipError as error:
        _render_error(file, error)
```

The CLI remains responsible for multiple-file behavior and accumulated exit
status.

### MCP

Conceptually, the MCP update tool should become:

```python
@server.tool()
def update(
    path: str,
    backup: bool = True,
    force: bool = False,
) -> dict:
    result = operations.update_file(
        Path(path),
        force=force,
        options=WriteOptions(backup=backup),
    )
    return _serialize_result(result)
```

The MCP tool may expose fewer policies than the CLI, but shared policies must have
the same semantics.

## Semantic Validation

CLI syntax parsing remains an adapter concern. For example, parsing the string
`10:50` belongs in `cli.py` because MCP already receives separate integer
parameters.

Semantic validation must be shared:

- Start and end lines must be positive where required.
- Start must not exceed end.
- Heading numbering style must be supported.
- Checksum algorithms must be supported.

The underlying domain function may perform this validation, or the application
operation may validate before calling it. It must not exist only in the CLI,
because that allows MCP to bypass it.

## Notices

Non-fatal conditions should be represented separately from errors. Examples:

- The document has a single h1 that may be a title.
- Heading numbering changed while a TOC placeholder exists.
- No AI placeholders matched a requested name.
- The document was already up to date.
- A Mermaid artifact changed while the Markdown file did not.

The application layer should return notice codes or plain notice objects. The CLI
may render them with Rich styling, while MCP may include them in structured
output.

Avoid making human-readable message text part of program logic.

## Mermaid Artifacts

`update_mermaid` differs from most functions in `markdown.py` because it writes
diagram files while processing the document.

For the initial refactoring:

- Retain its `dry_run` behavior.
- Retain collection through `written_files`.
- Have `update_document` return the collected paths as artifacts.

This is sufficient to unify CLI and MCP behavior.

A later, separate refactoring may make Mermaid return planned artifact writes
instead of writing immediately. That would permit document and artifact changes
to be committed as one transaction. It is useful but is not required for this
refactoring.

## Backup and Write Semantics

The shared application layer should define the following behavior:

| Situation | Backup | Document write | `changed` | `written` |
|---|---:|---:|---:|---:|
| Generated content is unchanged | No | No | False | False |
| Changed, dry-run enabled | No | No | True | False |
| Changed, backup enabled | Yes | Yes | True | True |
| Changed, backup disabled | No | Yes | True | True |
| Processing fails | No | No | N/A | N/A |

Tracking should be applied before comparing generated content with the original,
because tracking itself may create a document change.

The original content should be retained from the first read and used for backup.
There should be no second read solely for backup creation.

Atomic file replacement may be introduced here if desired, but it is not required
to complete the interface unification.

## Testing Strategy

The current test suite primarily tests functions in `markdown.py`. The
refactoring should add application and adapter coverage without duplicating all
domain tests.

### `tests/test_operations.py`

Test the shared application behavior:

- Missing path
- Directory supplied instead of a file
- Changed content
- Unchanged content
- Backup enabled and disabled
- No backup for unchanged content
- Dry-run
- Tracking
- Domain exception propagation
- Typed missing-placeholder handling
- Update phase order
- `force` propagation
- Mermaid artifact reporting
- Read-only check results

### CLI adapter tests

Use Typer's test runner and mock application operations. Verify:

- CLI options map to the correct application arguments.
- Multiple files are processed.
- Errors produce nonzero exit status.
- Dry-run results produce a diff.
- Notices and changed artifacts are rendered.

Do not retest Markdown transformation details in CLI tests.

### MCP adapter tests

Mock application operations. Verify:

- MCP parameters map to the correct application arguments.
- Structured results are serialized consistently.
- Application errors become MCP failures or agreed error objects.
- No MCP tool directly calls `markdown.py`.

### Parity tests

For operations exposed through both interfaces, verify that equivalent inputs
reach the same application operation with equivalent options.

The most important parity test is `update`, because its duplicated implementations
currently have meaningful behavioral differences.

## Migration Plan

The refactoring should be incremental so the existing test suite remains usable.

### Phase 1: Shared result and file mutation

1. Create `mdship/operations.py`.
2. Add `WriteOptions`, `OperationResult`, and `CheckResult`.
3. Add the internal shared file-edit helper.
4. Add tests for write, backup, no-op, tracking, and dry-run behavior.

### Phase 2: Canonical update pipeline

1. Move the update phase sequence from the CLI into `update_document`.
2. Add `update_file`.
3. Switch CLI `update` to `operations.update_file`.
4. Preserve existing CLI-visible behavior.
5. Switch MCP `update` to the same function.
6. Add parity and error-propagation tests.

This phase removes the highest-risk duplication first.

### Phase 3: Simple modifying operations

Migrate operations one at a time:

1. Fix and shift headings
2. Reflow and semantic line breaks
3. Number and unnumber headings
4. Add checksum
5. Standalone TOC, INCLUDE, and MERMAID

After each migration, remove the corresponding direct `markdown.py` imports from
both adapters.

### Phase 4: Read-only and AI operations

1. Check checksum
2. Validate links and AI placeholders
3. AI fix and check
4. AI context and update
5. Replace error-status strings with structured results or typed exceptions

### Phase 5: Adapter cleanup

1. Consolidate CLI result rendering.
2. Consolidate MCP result serialization.
3. Verify that adapters contain no document-processing workflows.
4. Update user documentation where CLI and MCP semantics have changed or become
   consistent.

## Completion Criteria

The refactoring is complete when:

- The complete update pipeline is defined in exactly one place.
- File reading, comparison, backup, dry-run, tracking, and writing are defined in
  exactly one place.
- Neither `cli.py` nor `mcp_server.py` directly imports transformation functions
  from `markdown.py`.
- Both interfaces call named operations from `operations.py`.
- Expected conditions use structured results or typed exceptions, not message
  prefix matching.
- MCP no longer suppresses arbitrary TOC processing errors.
- Unchanged MCP operations do not rewrite files or create unnecessary backups.
- Equivalent CLI and MCP calls produce equivalent document content.
- Existing domain tests continue to pass.
- New application and adapter tests cover the shared behavior.

## Non-Goals

This refactoring does not include:

- Plugin support
- Executing project-local Python code
- New placeholder types
- Rewriting every function in `markdown.py`
- Making every Markdown operation perfectly pure
- Redesigning the MCP protocol
- Requiring CLI and MCP to expose identical command sets
- A factory, registry, or dependency-injection framework

These concerns should not be mixed into the interface-unification work.

## Implementation Guidance for an AI Assistant

When using Codex, Claude, or another assistant to implement this plan:

1. Ask it to read this document, `mdship/cli.py`, `mdship/mcp_server.py`, and the
   relevant sections of `mdship/markdown.py`.
2. Start with Phase 1 and Phase 2 only.
3. Require tests before migrating additional commands.
4. Preserve unrelated working-tree changes.
5. Do not change placeholder syntax or documented processing order.
6. Compare CLI and MCP behavior explicitly after each migrated operation.
7. Keep `operations.py` free of Typer, Rich, and FastMCP dependencies.
8. Keep the initial implementation simple; split the module only if its size or
   responsibilities later justify it.
